# Ornament Craft — drawing SVG for the codex theme

Rules for keystones, corner rails, dividers and stat glyphs in
`src/components/codex/ornaments.tsx`. Every one of these was learned by drawing it wrong
first. Reference implementations, best first: `KhopeshKeystone`, `WingedDisc`,
`SerpentKeystone`, `ZigguratKeystone`, `BullKeystone`.

## 1. Solid mass, carved back out — not hollow outlines

**The rule that separates the good ornaments from the mediocre ones.** Anything meant to
read as a physical object (a blade, a serpent's body, a horn) is ONE solid
`fill="currentColor"` shape, with its internal detail carved back out as
`stroke="var(--ifm-background-surface-color)"` lines — fullers, scale ticks, growth rings.

Thin parallel outlines forming a hollow tube read as **bent wire**, not an object. That is
what made the first serpents and wings weak.

**Corollary:** carved detail must stop short of the silhouette edges. Scale ticks spanning
the full body width turned a snake into a dashed caterpillar.

### The exception: bold contour + internal motif

Rule 1 is about *thin parallel outlines*, not outlines generally. A **bold contour
enclosing a large area, filled with a structured internal motif**, is legitimate and much
lighter — see the scarab-wing treatment on `WingedDisc` (outlined wedge plus a band of
solid triangles).

Reach for it when a solid motif is too **dominant**: a solid shape can only be lightened
by trading weight against detail, whereas an outlined-with-motif shape stays light at any
size, and lets a neighbouring solid mass (the sun disc) keep the focal hierarchy.

## 2. Opaque backing

Any ornament overlapping a structural line (the card border, a divider rule) draws a
`fill="var(--ifm-background-surface-color)"` silhouette FIRST, so the line stops at the
ornament instead of running through it. Once the motifs are solid, a thin band along the
line is enough — the solid shapes mask themselves.

## 3. Terminations and proportion

- **A blade ends in a point; a wing ends in a tip.** Curling a terminal back on itself
  turns the motif into a decorative volute and the object read is lost entirely.
- **Give a motif enough depth to be itself.** A wing whose root depth is well under the
  disc diameter reads as a propeller blade; a corona whose rays do not reach ~2× the disc
  radius reads as a tuft of hair. If the viewBox cannot fit the needed proportion, grow
  the viewBox — it may be asymmetric about the border line — rather than shrinking the
  motif.
- **Straight beats swept next to a straight frame.** Angular geometry echoes the card's
  rectilinear frame and reads calmer than curves.

## 4. Variable-length ornaments: fixed terminal, variable shaft

Never scale a whole form with its length. A rail that simply tapers to a point couples
length to internal proportion, so the short version reads as a **shrunken copy** rather
than the same ornament.

Split it: a fixed-size head / blade / wave-period carrying all the detail, plus a plain
shaft that stretches. That is what lets `RAIL_LEN`'s asymmetric edge/side reaches read as
one design.

**Why the reaches are asymmetric at all:** a card's width is effectively unbounded, so the
top rail can run long; its height is not, because the top and bottom corners both reach
down the same side, so two side rails plus a comfortable gap must fit inside the family's
*shortest* card or they meet in the middle and read as one continuous line.

## 5. CSS `rotate()` transposes an SVG's axes

The four `CardFrame` corners are oriented by CSS rotation, so at 90°/270° (`tr`, `bl`) the
SVG's +x becomes the screen's vertical. Asymmetric rails silently come out with the long
one running down the side.

Invisible while both rails are equal length, and invisible if you only inspect the
top-left corner. **Verify all four by measuring rendered ink extents in the browser, not
by eye.**

## 6. Mirror symmetry must be by construction

A pair of flanking elements must be generated by ONE function, parameterised by distance
measured **outward from the centre** — not by a single global coordinate. The first
guilloche braid referenced a global x, which left the two flanks at unrelated phases and
visibly asymmetric.

Where a form repeats (a braid, a wave), give it a **fixed period** so a longer rail grows
more undulations rather than stretching the same two.

## 7. Hierarchy

- **The concentric focal belongs to the primary ornament alone** — ring, gap, core is
  reserved for the winged-disc keystone. Every subordinate mark (corner bosses, crossing
  bosses, summit shrines) stays a single solid shape, so it cannot compete. Hierarchy over
  uniformity.
- **Detail runs along edges, never inward.** Ornament detail hugs the frame; secondary
  lines must not point into the content panel.
- Rigid rectilinear structure (rails, frames, diamonds) carries slightly organic carved
  detail (scallops, tapers, concave bosses) — the "carved stone plus inlaid brass" read.

## 8. Abstraction level

At the sizes these render (~80–90px wide, features a few pixels across),
**representational detail turns comic rather than carved.** The bull keystone's first pass
had a muzzle line and nostrils and read as a cartoon; two eye slots under a brow band read
as a votive mask.

If a feature is smaller than about 3px, it is texture, not anatomy — draw it as rhythm
(ticks, bands, pips) or leave it out.

## 9. Layout consequences

A keystone hangs above the card's top edge, and the card's own `margin-top` is the only
clearance between that overhang and the card stacked above. The family's usual `1.4rem`
(22.4px) suits ~14–16px of overhang. A taller motif needs the margin raised to match — the
ziggurat overhangs 20.3px and would have sat ~2px off the card above at the default.

Keep the CSS `width`/`height` ratio equal to the viewBox ratio, and set `top` to
`(borderLineY / viewBoxHeight) * renderedHeight`.

## 10. Mechanics

- All stroke and fill uses `currentColor` so an ornament tints per theme; the container
  sets the colour.
- `strokeLinejoin="round"` for smooth carved joins.
- Decorative ornaments are `aria-hidden`.
- Flat only — see the no-shadow rule in SKILL.md.
- Generate repeated geometry in code (a loop emitting path strings) rather than
  hand-authoring coordinates: hand-authored arcs drift, and parametric geometry keeps
  proportions honest when a size changes.
